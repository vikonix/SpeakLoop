# Выбор параметров модели и работа на слабом компьютере

Документ относится к этапу 2 плана переработки (`docs/refactoring.md`).
Место в проекте: `docs/model-parameters.md`.

Документ отвечает на три вопроса:

1. какая модель используется и откуда она взята;
2. какие параметры передаются серверу модели и почему именно такие;
3. что происходит на слабом компьютере и что может сделать его владелец.

Все числа в документе получены измерением на реальном оборудовании.
Раздел 4 содержит команды и результаты. Расчётные значения помечены словом
"оценка".

## 1. Модель

| Свойство | Значение |
| --- | --- |
| Файл | `models/gemma-4-12B-it-QAT-Q4_0.gguf` |
| Размер файла | 6 975 878 560 байт (6,50 ГиБ, 6653 МиБ) |
| Размер тензоров | 6,48 ГиБ (6635 МиБ), по данным `llama-bench` |
| Репозиторий | `lmstudio-community/gemma-4-12B-it-QAT-GGUF` |
| Исходная модель | `google/gemma-4-12B-it-qat-q4_0-unquantized` |
| Квантование | Q4_0, QAT, сборка llama.cpp b10069 |
| Архитектура | `gemma4`, 11,91 млрд параметров |
| Слоёв | около 52 (оценка, см. раздел 5) |

Мультимодальная проекция (`mmproj-gemma-4-12B-it-QAT-BF16.gguf`, 175 МБ) лежит
в репозитории отдельным файлом. SpeakLoop её не использует и не загружает.

Сервер модели: `llama-server` сборки b10099. Она новее сборки, которой сделано
квантование, поэтому файл читается без ошибок.

### 1.1 Режим размышления

Gemma 4 имеет настраиваемый режим размышления. Для голосового урока этот режим
должен быть выключен. При скорости около 5 токенов в секунду каждая сотня
служебных токенов добавляет 20 секунд к ответу.

Шаблон чата модели управляет режимом через переменную `enable_thinking`. Если
она истинна, шаблон вставляет `<|think|>` в начало системного сообщения. Если
нет, шаблон добавляет после `<|turn>model` пустой канал размышления, и модель
отвечает сразу.

`llama-server` сборки b10099 по умолчанию передаёт в шаблон
`enable_thinking=true`. Размышление он отделяет в поле `reasoning_content`,
которое SpeakLoop не читает, поэтому в окне его не видно, но время оно
занимает (раздел 4.8). Выключается параметром запроса
`chat_template_kwargs: {"enable_thinking": false}`. Приложение передаёт его
с шага 2b, и только для бэкенда `llama-server`.

Переключатель в LM Studio относится только к LM Studio.

## 2. Эталонное оборудование

Измерения сделаны на ноутбуке. Ноутбук не является основной машиной. Он служит
образцом слабого компьютера.

| Свойство | Значение |
| --- | --- |
| Видеокарта | NVIDIA GeForce GTX 1650 Ti, 4095 МиБ, вычислительная способность 7.5 |
| Память | 64 ГБ DDR4, два модуля |
| Система | Windows |
| Зарезервировано оборудованием | 161 МБ видеопамяти |

Основная машина проекта имеет RTX 3090. На ней модель размещается в
видеопамяти целиком, и выводы раздела 7 к ней не относятся.

Карта поколения Turing не имеет тензорных ядер. Готовая сборка llama.cpp
сообщает об этом при запуске и предлагает собрать llama.cpp самостоятельно с
ключом `GGML_CUDA_FORCE_MMQ`. Проект этого не делает: своя сборка нарушает
привязку к готовому выпуску с проверкой sha256, а выигрыш относится в основном
к обработке промпта, которая и так достаточно быстра.

## 3. Итоговые параметры

Сервер модели получает следующие аргументы, дополнительно к тем, которые уже
передаются с шага 1c.

| Аргумент | Значение | Причина |
| --- | --- | --- |
| `-c` (`--ctx-size`) | 16384, ключ `external_n_ctx` | размер контекста урока |
| `-fitc` | равен `-c` | нижняя граница контекста для автоматического подбора |
| `-ngl` (`--n-gpu-layers`) | не передаётся при `external_n_gpu_layers: "auto"` | подбор llama.cpp выбирает число слоёв сам |
| `-fitt` | не передаётся | значение по умолчанию, см. раздел 6.2 |

Команда запуска из журнала приложения (2026-09-15):

```
llama-server.exe -m models\gemma-4-12B-it-QAT-Q4_0.gguf --host 127.0.0.1 --port 8765 --ctx-size 16384 -fitc 16384 --parallel 1 --cache-reuse 256 --api-key local --no-ui
```

Сервер принял `-fitc` и сообщил через `/props` контекст 16384.

`--cache-reuse 256` для этой модели не действует: сервер пишет
`cache_reuse is not supported by this context, it will be disabled`. Ключ
оставлен, потому что он нужен запасной модели llama-3.2-3b. Обычный кэш
префикса при этом работает (раздел 4.7).

### 3.1 Автоматический подбор

llama.cpp в закреплённой сборке b10099 подбирает незаданные параметры под
свободную видеопамять (ключ `-fit`, по умолчанию включён). Подбор прекращается,
если пользователь задал `-ngl` явно.

Проект использует это как готовое поведение. Своя формула расчёта слоёв не
пишется: подбор знает реальную структуру модели и видит свободную память в
момент запуска.

### 3.2 Ручное переопределение

Ключ `external_n_gpu_layers` в `settings.json` служит ручным
переопределением. Допустимые значения совпадают с тем, что принимает `-ngl`:
`"auto"`, `"all"` или целое число от 0. Неверное значение заменяется на
`"auto"` с сообщением в консоли.

`config/hardware_config.json` число слоёв и контекст больше не содержит.
Файл, записанный до этапа 2, ещё хранит `EXTERNAL_N_GPU_LAYERS` и
`EXTERNAL_N_CTX`; приложение эти ключи не читает.

При значении `auto` аргумент серверу не передаётся, и работает подбор. При
числе или `all` значение передаётся как есть, и подбор отключается сам.

### 3.3 Защита контекста

Подбор при нехватке памяти уменьшает контекст без сообщения об ошибке. Ключ
`-fitc` задаёт границу, ниже которой подбор опускать контекст не имеет права.
Проект передаёт `-fitc` равным запрошенному контексту, поэтому подбор жертвует
слоями, а не длиной урока.

Приложение после запуска читает фактический контекст через `/props`. Если он
меньше запрошенного, приложение пишет предупреждение в журнал и строку
[System] в чат. Строка состояния для этого не годится: следующая смена
состояния окна сразу её перезаписывает. Урок при этом продолжается.

Проверка того, что `-fitc` действительно нужен при явном `-c`, не делалась:
возможно, подбор и без него не трогает контекст, заданный пользователем.
Ключ передаётся в любом случае, вреда от него нет.

### 3.4 Устройства речи

`detect_hardware` переносит синтез (Kokoro) на процессор, если модель
использует видеокарту и её память меньше 12 ГБ (`TTS_GPU_MIN_VRAM_GB`). Порог
выбран с запасом: веса около 6,5 ГиБ, контекст и буферы вычислений сверху, и
Kokoro открывает свой контекст CUDA.

Распознавание (Whisper large-v3-turbo) под это правило не попадает с шага 3b
(`docs/refactoring.md`, раздел 8.1): оно работает на видеокарте всегда, когда
ctranslate2 её видит, в режиме `int8_float16` (веса около 0,8 ГБ). Whisper
загружается до запуска `llama-server`, поэтому подбор слоёв видит уже занятую
им память и отдаёт модели меньше слоёв. Если ответы модели от этого заметно
замедлились, `"stt_device": "cpu"` в `config/settings.json` переносит
распознавание на процессор.

Если сборка `llama-server` видеокарту не использует, карта остаётся модулям
речи при любом объёме. `DEVICE` по-прежнему означает только "torch видит
CUDA"; устройства речи записаны в `STT_DEVICE` и `TTS_DEVICE`.

На эталонном ноутбуке: `DEVICE = cuda`, `STT_DEVICE = cuda` (до шага 3b
было `cpu`), `TTS_DEVICE = cpu`.

## 4. Проверки

Все проверки выполнены на эталонном ноутбуке с моделью из раздела 1.

### 4.1 Скорость обработки промпта

```
llama-bench -m models\gemma-4-12B-it-QAT-Q4_0.gguf -ngl 12 -p 2048 -n 128
```

Результат: 52,77 токена в секунду при 12 слоях на видеокарте.

Вывод: обработка длинного промпта проблемой не является. Промпт урока
занимает около 2300 токенов, это примерно 44 секунды. Плата разовая: сервер
хранит обработанную часть в кэше слота, и каждая следующая реплика ученика
добавляет 30-100 токенов. (`--cache-reuse` к этому не относится, для Gemma он
отключён, см. раздел 3.)

Поправка по замерам в приложении (разделы 4.7 и 4.8): короткие порции
обрабатываются намного медленнее, около 10-21 токена в секунду (36 токенов за
3,5 секунды). Поэтому каждая реплика ученика добавляет к ответу 3-10 секунд
обработки промпта, а не доли секунды.

### 4.2 Скорость генерации и число слоёв

```
llama-bench -m models\gemma-4-12B-it-QAT-Q4_0.gguf -ngl 0,12,20 -p 0 -n 64 -r 1
```

| Слоёв на видеокарте | Токенов в секунду | Прирост |
| --- | --- | --- |
| 0 | 4,53 | - |
| 12 | 5,19 | 15 % |
| 20 | 6,50 | 43 % |

Вывод: прирост от переноса слоёв на видеокарту держится до 20 слоёв. Он есть,
но он не решающий: даже лучший результат остаётся в пределах 6-7 токенов в
секунду.

### 4.3 Влияние заполненного контекста

```
llama-bench -m models\gemma-4-12B-it-QAT-Q4_0.gguf -ngl 20 -p 0 -n 64 -d 0,4096 -r 1
```

| Глубина контекста | Токенов в секунду |
| --- | --- |
| 0 | 6,39 |
| 4096 | 4,88 |

Значение для глубины 0 (6,39) расходится с разделом 4.2 (6,50) при тех же
условиях. Это разброс одиночных прогонов (раздел 8, пункт 2).

Вывод: заполнение контекста до 4096 токенов снижает скорость на 24 процента.
Урок начинается с промпта в 2300 токенов и растёт дальше, поэтому расчётной
скоростью следует считать нижнее число, а не верхнее.

### 4.4 Проверка запуска сервера

```
llama-server -m models\gemma-4-12B-it-QAT-Q4_0.gguf -ngl 20 -c 16384 --port 8765
```

Сервер загрузил модель за 16,3 секунды и принял соединения. Сообщений о
нехватке памяти нет.

В журнале отмечены два наблюдения:

- `n_slots = 4` по умолчанию. Проект передаёт `--parallel 1`, поэтому слот
  будет один и получит весь контекст.
- Предупреждения о токенах `<|tool_response>` и `</s>`. В метаданных этой
  сборки GGUF типы токенов заданы неточно. llama.cpp исправляет это сам и
  правит список токенов конца генерации. Предупреждения безвредны: в шаблоне
  чата `<|tool_response>` действительно завершает генерацию после вызова
  инструмента, а обычные ответы в разделе 4.7 закончились штатно.

### 4.5 Фактический расход видеопамяти

```
nvidia-smi --query-gpu=memory.used,memory.total --format=csv
```

Результат при работающем сервере с 20 слоями: 3785 МиБ из 4096.

Диспетчер задач в это же время показал: выделенная память видеокарты 3,7 из
4,0 ГБ, общая память видеокарты 0,9 ГБ при плоском графике.

Вывод: 20 слоёв размещаются в видеопамяти по-настоящему. Значение общей памяти
относится к закреплённым буферам на стороне процессора, а не к вытеснению
весов. При вытеснении этот график растёт по мере работы.

Свободными остаются 311 МиБ. Этого мало: любое окно браузера или предпросмотр
в проводнике может вытеснить часть весов в системную память. Поэтому 20 слоёв
не годятся как значение по умолчанию.

### 4.8 Режим размышления

Один и тот же запрос к серверу (системное сообщение и "Hello, how are you?")
два раза:

| Запрос | Токенов ответа | `reasoning_content` | Генерация |
| --- | --- | --- | --- |
| `chat_template_kwargs: {"enable_thinking": false}` | 15 | нет | 2,7 с (5,6 т/с) |
| без параметра (по умолчанию) | 184 | есть | 40,4 с (4,6 т/с) |

Ответы по смыслу одинаковые. Вывод: сервер по умолчанию включает размышление,
параметр запроса его выключает, и короткая реплика становится быстрее
примерно в 7 раз.

Во втором запросе `cache_n = 0`: с размышлением шаблон вставляет `<|think|>`
в начало системного сообщения, и префикс уже не совпадает с первым запросом.

### 4.9 Обработка коротких промптов

Урок после шага 2b (размышление выключено, восемь реплик, 2026-09-15):
реплика ученика из 33-35 токенов обрабатывалась 3,3-3,5 секунды, реплика из
133-140 токенов (после обрезки истории) 4,8-4,9 секунды. Генерация ответа из
9-17 токенов заняла 1,5-3,4 секунды при 5,1-5,9 токена в секунду, ответ модели
целиком 5,6-7,1 секунды. `nvidia-smi` во время урока: 3017 МиБ из 4096.

Журнал сервера показывает причину: сервер откладывает последние 4 токена
промпта, и первый пакет содержит 30 токенов:

```
prompt processing, n_tokens = 30, progress = 0.98, t = 3.05 s
```

ggml считает пакет на видеокарте (при частичной выгрузке это перенос весов
процессорных слоёв, "op offload"), только если в нём не меньше 32 токенов.
Пакет из 30 токенов считается на процессоре.

```
llama-bench -m models\gemma-4-12B-it-QAT-Q4_0.gguf -ngl 10 -p 16,34,64,140 -n 0 -nopo 0,1 -r 2
```

| Токенов | С переносом (`nopo 0`) | Только процессор (`nopo 1`) |
| --- | --- | --- |
| 16 | 12,77 т/с | 12,57 т/с |
| 34 | 21,97 т/с (1,55 с) | 12,16 т/с (2,80 с) |
| 64 | 32,89 т/с (1,95 с) | 13,05 т/с |
| 140 | 41,54 т/с (3,37 с) | 13,55 т/с (10,3 с) |

Вывод: перенос выгоден начиная с 32 токенов, `--no-op-offload` не нужен.
Постоянная плата переноса около 1 секунды плюс около 17 мс на токен.

Порог задаётся переменной окружения `GGML_OP_OFFLOAD_MIN_BATCH`:

```
set GGML_OP_OFFLOAD_MIN_BATCH=16
llama-bench -m models\gemma-4-12B-it-QAT-Q4_0.gguf -ngl 10 -p 16,24,30 -n 0 -r 2
```

| Токенов | Порог 16 | Порог по умолчанию (32) |
| --- | --- | --- |
| 16 | 13,23 т/с (1,21 с) | 12,33 т/с (1,30 с) |
| 24 | 17,87 т/с (1,34 с) | 12,65 т/с (1,90 с) |
| 30 | 20,42 т/с (1,47 с) | 11,89 т/с (2,52 с) |

Вывод: при пороге 16 пакет из 30 токенов обрабатывается на секунду быстрее.
На 16 токенах оба пути стоят одинаково, поэтому ниже 16 порог не опускается.
Приложение передаёт серверу `GGML_OP_OFFLOAD_MIN_BATCH=16` (значение,
выставленное владельцем перед запуском, сохраняется). При модели целиком в
видеопамяти и в сборке для процессора переменная ни на что не влияет.

Проверка уроком (пять реплик, 2026-09-16; в `main.log` строка
`LLM server environment: GGML_OP_OFFLOAD_MIN_BATCH=16`):

| Запуск | Токенов промпта | Обработка | Скорость |
| --- | --- | --- | --- |
| Порог 32 (урок из раздела 4.9 выше) | 33-35 | 3,3-3,5 с | около 10 т/с |
| Порог 16 | 31-40 | 2,8-3,4 с | 11,2-11,9 т/с |

Вывод: выигрыш около 15 процентов (84-90 мс на токен вместо 100-104), а не
ожидавшиеся 1,5 секунды. Ответ модели целиком занял 5,8-6,8 секунды, так же,
как до правки: генерация в этом прогоне шла немного медленнее (4,9-5,3 т/с).
Порог оставлен, вреда от него нет.

Сервер обрабатывает 30-40 токенов примерно за 3 секунды, а `llama-bench`
30 токенов за 1,5 секунды. Причина разницы не установлена. Возможные
причины: последние 4 токена по-прежнему идут через процессор, запись
контрольной точки кэша для скользящего окна внимания, другое число слоёв на
видеокарте, расходы самого сервера. Разобраться можно по подробному журналу
сервера (`-lv 4`); выигрыш не больше секунды (раздел 9).

## 5. Расчёты

Два замера из раздела 4.6 дают цену слоя:

```
(1024 - 512) / (11 - 7) = 128 МиБ на слой
```

Отсюда число слоёв модели:

```
6635 МиБ / 128 МиБ = около 52 слоёв
```

6635 МиБ здесь размер тензоров модели (6,48 ГиБ, раздел 1); файл чуть больше
за счёт метаданных. Точное число слоёв сервер пишет при загрузке (`n_layer`)
при подробном журнале.

Оптимум в 18 слоёв тоже оценка, а не замер: измерены 20 слоёв со свободными
311 МиБ (раздел 4.5), и два слоя меньше дают около 567 МиБ, то есть запас из
раздела 7.3.

Отсюда же запас, при котором подбор выдал бы оптимум в 18 слоёв:

```
512 - (18 - 11) * 128 = -384 МиБ
```

Значение отрицательное, то есть ключом `-fitt` измеренного оптимума достичь
нельзя. Встроенная оценка считает по худшему случаю для вычислительных
буферов, и её расхождение с измерением составляет примерно 700-900 МиБ.

## 6. Обоснование решений

### 6.1 Почему подбор, а не своя формула

Своя формула потребовала бы хранить в каталоге моделей число слоёв и расход
памяти на токен контекста. Эти поля пришлось бы заполнять для каждой новой
модели, и точность всё равно осталась бы ниже, чем у подбора. Подбор читает
метаданные файла и смотрит на свободную память в момент запуска.

### 6.2 Почему ключ запаса не используется

Ключ `-fitt` вводился как способ получить больше слоёв на слабой карте.
Измерение показало, что его предел составляет 11 слоёв против оценки в 18
(раздел 5). Задачу он не решает, а настройку добавляет. Поэтому используется
значение по умолчанию, а ручное переопределение делается числом слоёв.

### 6.3 Почему ручное переопределение сохранено

Подбор с запасом по умолчанию выбирает 7 слоёв (раздел 4.6). Разница между 7
слоями и 18 составляет около 25 процентов скорости (оценка по разделу 4.2:
около 4,9 и 6,2 токена в секунду). На машине, где модель размещается целиком,
разницы нет. Настройка нужна тому, кто
измерил свой компьютер и готов следить за свободной видеопамятью.

Тот же ключ служит лекарством в редком случае, когда подбор при запуске
работает слишком долго. Явное число слоёв отключает подбор.

## 7. Работа на слабом компьютере

Слабым считается компьютер, в видеопамять которого модель не помещается
целиком. Для модели из раздела 1 это любая карта меньше 8 ГБ (оценка: веса
6,5 ГиБ плюс контекст и буферы; карта на 8 ГБ не проверялась).

### 7.1 Чего ожидать

Эталонный ноутбук при автоматическом подборе. Замеры из разделов 4.7-4.9,
остальное помечено как оценка:

| Величина | Значение |
| --- | --- |
| Скорость генерации, начало урока (без размышления) | 4,9-5,9 токена в секунду |
| Скорость генерации, середина урока | около 4 токенов в секунду (оценка) |
| Обработка реплики ученика (30-40 токенов) | 2,8-3,5 секунды |
| Короткая реплика модели (9-19 токенов), целиком | 5,6-7,1 секунды |
| Реплика в 60-120 токенов | 15-30 секунд (оценка) |
| Та же короткая реплика с размышлением (до шага 2b) | 44-58 секунд |
| Первая обработка промпта урока | около 44 секунд, один раз за урок (оценка) |
| Распознавание фразы (процессор) | около 2 секунд |
| От последнего слова до голоса ответа | 12-13 секунд, из них 3 секунды ожидание тишины |
| Загрузка модели | 9-16 секунд |
| От старта приложения до готового окна | 24-53 секунды (первый запуск дольше) |

Урок физически возможен, но темп получается как в переписке, а не как в
разговоре. Для разговорного темпа нужна карта, в которую модель помещается
целиком.

### 7.2 Обязательные условия

1. Режим размышления выключен. При 5 токенах в секунду он один способен
   добавить минуту к каждой реплике (раздел 4.8: 40 секунд на реплику из 15
   токенов).
2. Синтез речи работает на процессоре, `detect_hardware` делает это сам
   (раздел 3.4). Синтез предложения занимает около 0,85 секунды, и на фоне
   ответа модели это незаметно. Распознавание с шага 3b работает на
   видеокарте в режиме `int8_float16` и занимает часть её памяти. Whisper
   small на процессоре обрабатывал фразу за 2 секунды (раздел 4.7);
   large-v3-turbo на процессоре должен быть заметно медленнее (не измерено).
   64 ГБ оперативной памяти держат оба модуля без труда.

### 7.3 Как измерить свой компьютер

Порядок для владельца слабой машины, который хочет поднять число слоёв руками.
Утилиты лежат в `bin/llama/`.

1. Закрыть программы, которые держат видеопамять.
2. Узнать оценку подбора:

   ```
   llama-fit-params -m models\<модель>.gguf -c 16384
   ```

3. Измерить скорость для оценки подбора и для нескольких значений выше:

   ```
   llama-bench -m models\<модель>.gguf -ngl 7,12,20 -p 0 -n 64 -r 1
   ```

4. Запустить сервер с выбранным числом слоёв и проверить расход памяти:

   ```
   llama-server -m models\<модель>.gguf -ngl 20 -c 16384 --port 8765
   nvidia-smi --query-gpu=memory.used,memory.total --format=csv
   ```

5. Оставить не менее 500 МиБ свободной видеопамяти. Записать выбранное число
   слоёв в `settings.json`, например `"external_n_gpu_layers": 18`.

### 7.4 Главная опасность

Драйвер NVIDIA на Windows при нехватке видеопамяти не возвращает ошибку. Он
переносит часть весов в системную память. Программа продолжает работать, но
скорость падает в разы, и ни одного сообщения об этом нет.

Признак: результат для большего числа слоёв хуже, чем для меньшего. Второй
признак: график общей памяти видеокарты в Диспетчере задач растёт по мере
работы.

Из-за этого свободный запас важнее лишних двух слоёв.

## 8. Ограничения измерений

1. `llama-bench` без ключа `-c` работает с контекстом 512 токенов. Кэш ключей и
   значений при этом почти не занимает памяти. Реальные скорости в уроке ниже
   измеренных, а не выше. Поправка получена отдельно в разделе 4.3.
2. Измерения сделаны с одним повтором (`-r 1`). Разброс между повторами не
   известен.
3. `llama-bench` не применяет шаблон чата. Режим размышления на его числа не
   влияет, а на длительность реального ответа влияет сильно.
4. Число слоёв модели (52) получено расчётом из двух точек, а не прочитано из
   метаданных.
5. Замеры в приложении (разделы 4.7 и 4.9) сделаны по коротким репликам
   (2, 8 и 5 реплик) в начале урока, со старым коротким промптом. Длинный
   промпт урока (этап 3) и заполненный контекст не проверялись.

1. Сколько слоёв выбирает подбор при запуске из приложения, и почему скорость

   `"external_n_gpu_layers": 18`. Сравнивать после выключения размышления.

   пригодился бы для журнала.
3. Поведение подбора на основной машине с RTX 3090.
4. Почему сервер обрабатывает короткий промпт вдвое медленнее, чем
   `llama-bench` (раздел 4.9).
5. Работа с LM Studio после шага 2b (запрос без дополнительных полей).

Проверено и закрыто: способ выключения размышления (раздел 4.8, в приложении
с шага 2b), приём ключа `-fitc` сервером (раздел 3), системная роль в
шаблоне чата (`supports_system_role: true`, свой шаблон не нужен), параметры
выборки (шаг 2b: `temperature 1.0`, `top_p 0.95`, `top_k 64`, как рекомендует
GGUF Gemma; ответы в уроке короткие и простые), `--no-op-offload` (не нужен,
раздел 4.9).
